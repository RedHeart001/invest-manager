## 2. 为什么必须分成"构建"与"切换"两个阶段

候选构建不触碰运行中的容器；切换才改变现实。两者失败后果不同，回退代价也不同：

- 构建失败 ⇒ 正式服务零影响，取消即可。
- 切换失败 ⇒ 必须成套回滚，且要同时恢复代理配置（否则变成"旧代码＋新代理"，不是原现场）。

因此顺序固定：**构建 → 候选自检 → 隔离验收 → 切换 → 硬判据核验 → 恢复监测**，任一步未过就停在该步。

### 9.2 切换期间修掉的两处检查器缺陷（不是候选镜像回归）

隔离验收首轮在「DS uvicorn 服务进程非 root」上红，读数 `uid=0,1000`。逐层复现后确认是 `scripts/verify-compose-isolated.mjs` 自身缺陷，**与候选镜像无关**：

1. **子串匹配自匹配**：检查脚本自己是 `python -c <文本>`，而那段文本里必然含 `uvicorn app.main:app` 字面量 ⇒ 扫描 `/proc` 时把这条 root 的内联进程当成"服务进程"。**用旧码容器 `cr1049-accept` 跑同一段脚本同样得到 `uid=0,1000`**，因此不是新码回归。改为按**参数位**判定（argv 里有 `uvicorn`／`*/uvicorn` 且含 `app.main:app` 参数）。
2. **内联 SQL 转义**：`print(c.execute(\\\"select …\\\").fetchone()[0])` 在 Windows 下经 `spawnSync → docker CLI` 后被吃成 Python 源码里的裸反斜杠 ⇒ `SyntaxError: unexpected character after line continuation character`。改为参数化查询（`execute('… where code=?', ('A3SYNTH',))`），不再往 SQL 里拼字面量。
3. **与实际常驻监测抢同一目录**：最后一条「开发 DB/runtime/backups 前后指纹不变」对 `data-service/runtime` 做逐字节比对，而该目录是**宿主侧 watcher 每 30 秒自写**的（实测 45 秒内 3 个文件变化），且 compose 对它没有 bind mount ⇒ 只要监测在跑就必然为红。改为：该目录只查**是否新增或丢失文件**（隔离若真写到这里，形态是新建状态文件），其余路径仍逐字节严格比对。

以上三处都是"检查器把自己的行为算成了被测对象"，修完 30/30 全绿；候选镜像未因此改动一行。

### 9.3 凌晨窗口的伴随进程（2026-11-28 01:0x 就位）
