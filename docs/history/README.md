# 历史归档索引（docs/history/）

> **这是什么**：**操作记录**——逐项做法、改动文件清单、一次性操作指引、被推翻的计划。
> 归档文件**只增不改**，不要在这里维护"最新状态"，状态只在上层文件里。
>
> **上层文件分工**：
> - [../PLAN.md](../PLAN.md) —— 需求与设计（唯一来源）
> - [../PROGRESS.md](../PROGRESS.md) —— 进度账本（唯一来源）
> - [../CONSTRAINTS.md](../CONSTRAINTS.md) —— 不得回退的约束与数据源事实
> - [../CODE-REVIEW.md](../CODE-REVIEW.md) —— 各轮发现了什么
> - [../FIX-LEDGER.md](../FIX-LEDGER.md) —— 每项修了没、怎么验的

## 什么时候建归档

| 触发 | 判据 | 性质 |
|---|---|---|
| **压缩触发** | 上层文件因压缩不再承载这段原文 | 机械，必进 |

**不采用"每个任务都归档"**：`PROGRESS.md` 已是执行记录（一行/天）。两个都记全部任务就变成同一事实两处；
而且绝大多数任务的明细事后无价值——CR6 明细有价值，恰恰因为它**先被压缩了**，归档填的是那个信息落差。

## 规模上限与压缩

**阈值：单个归档文件 ≥ 500 行**——按文件单独判定，与目录合计无关。检查命令：

```bash
wc -l docs/history/*.md
```

**时机：每次写入归档文件时自查行数**。超阈值就**就地精炼该文件**——保留文件与事件快照结构
（背景 / 逐项做法 / 验证 / 改动文件清单），删掉冗余过程明细。**不塌缩成索引一行、不删文件**，
精炼完再提交。

原文由 git 历史兜底，可取回：`git show <commit>:docs/history/<file>`。

**归档文件照旧写事件快照**（背景 / 逐项做法 / 验证 / 改动文件清单）。

⚠️ 「一次性操作指引（留档，勿再执行）」这类内容必须显式标注，避免后来人照做踩坑。

> 本规范自 2026-09-21 起生效，**老归档不回改**（CR1/CR3/CR6/ops 四份保持原样）。
