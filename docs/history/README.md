# 历史归档索引（docs/history/）

> **这是什么**：**执行任务的记录**——逐项做法、改动文件清单、一次性操作指引、被推翻的计划；
> 同时是 `.claude/skills/` 项目技能**提炼的原料**。
> 归档文件**只增不改**，不要在这里维护"最新状态"，状态只在上层文件里。
>
> **上层文件分工**：
> - [../PLAN.md](../PLAN.md) —— 需求与设计（唯一来源）
> - [../PROGRESS.md](../PROGRESS.md) —— 进度账本（唯一来源）
> - [../CONSTRAINTS.md](../CONSTRAINTS.md) —— 不得回退的约束与数据源事实
> - [../CODE-REVIEW.md](../CODE-REVIEW.md) —— 各轮发现了什么
> - [../FIX-LEDGER.md](../FIX-LEDGER.md) —— 每项修了没、怎么验的

## 什么时候建归档（双触发判据）

| 触发 | 判据 | 性质 |
|---|---|---|
| **压缩触发** | 上层文件因压缩不再承载这段原文 | 机械，必进 |
| **模式触发** | **同一做法第 2 次出现** | 机械，可判定 |

> **一次是事件，两次是模式。模式才值得留。**
> 第一次做某件事只是个事件，`PROGRESS.md` 一行足够；第二次遇到同类问题说明它会再来，
> 这时才建归档，并在文件里标注"这是第 N 次"。

**不采用"每个任务都归档"**：`PROGRESS.md` 已是执行记录（一行/天）。两个都记全部任务就变成同一事实两处；
而且绝大多数任务的明细事后无价值——CR6 明细有价值，恰恰因为它**先被压缩了**，归档填的是那个信息落差。

## 归档文件的结构要求

````markdown
# <事件名>（<日期>）

## 背景 / 逐项做法 / 验证     ← 照旧
...

## 可复用的做法
- **信号** … → **判断** … → **动作** … → **验证** …
- （没有可复用做法就写"无"）
````

**`## 可复用的做法` 是 skill 提炼的接口，必须在写记录当时就写。**
归档是"发生了什么"（事件快照：日期/commit/改了哪些文件），skill 需要"该怎么干"（信号→判断→动作→验证），
两者不是一回事。指望事后从叙述里捞方法，要重读全文重新抽象，**而且会漏**。

⚠️ 「一次性操作指引（留档，勿再执行）」这类内容对 skill 提炼是**负资产**——照做会踩坑，必须显式标注。

**提炼方式**：扫所有归档的 `## 可复用的做法` 小节，看哪条**重复出现**——重复即够格提炼为
`.claude/skills/<name>/SKILL.md`。

> 本规范自 2026-09-21 起生效，**老归档不回改**（CR1/CR3/CR6/ops 四份保持原样）。
