# CR10-49 美股完整名单持久化续跑与幂等发布方案（2026-11-26）

> 状态：**代码与离线门禁已完成（2026-11-26）；正式容器装载与自然 02:00 窗口待后续，不人工触发。**
> 触发事实：11-26 启动补跑 `partial_failed`，us 腿在 1500s 内只处理 441/923 页，整腿 deadline 后被批量补记为 4,368 条失败；旧数据正确保留。单纯抬预算、削重试或放宽闸门均不能消除同类失败。
> 原始失败保留：11-26 的 `partial_failed`、us 1500s、441/923 页与 4,368 条补记**不改写**；本方案的结果只证明新架构的离线行为，不把旧轮翻成已通过。

## 1. 目标与边界

### 1.1 目标

把美股完整名单从“一次 HTTP 请求内必须翻完 923 页”改为“持久化采集任务自动续跑、完整候选幂等发布”：

- 上游暂时缓慢、DNS 抖动、502、读超时或进程重启，不再直接成为 us `partial_failed`；
- 每成功一页立即落检查点，重启后从缺口继续，不重复购买已完成页；
- 正式 `Product` 在完整候选通过全部验证前零写入；
- 采集期间旧数据正常可用；
- 完整候选最终由 Web 原子替换，并只刷新一次 us 行情；
- 不人工 `POST /sync/run` 凑自然轮，不放宽 70% 缩水闸、空载荷保护、声明稳定、去重、穷尽空页或重试次数。

### 1.2 诚实边界

外部上游永久不可用或接口永久变更时，系统不能凭空得到新名单。此时必须保留旧数据并显示 `waiting/blocked/stale`，不得伪装 `completed`。第二完整名单源是后续独立任务；现有 openbb/Tencent/Sina 注册属于行情备源，不是完整名单备源。

## 2. 总体结构

```text
02:00 每日调度 / 启动补跑
  ├─ fund/stock/bond/crypto/hk：沿用现有同步与刷新
  └─ us：启动或恢复持久化采集任务
         ↓
      每页成功 → 原子写检查点
         ↓
      网络异常 → waiting，按退避自动继续
      进程重启 → 读取检查点继续
         ↓
      页义务 / 声明稳定 / 去重 / 穷尽空页全部通过
         ↓
      candidate_ready
         ↓
      Web 按 snapshotId 幂等事务发布
         ↓
      单独刷新 us 行情
         ↓
      completed
```

健康日可当日完成；慢日显示 `collecting/waiting`，不再因为 1500s 到期生成 us 失败。

## 3. DS 持久化任务

### 3.1 模块与落点

新增 `data-service/app/us_list_job.py`。

生产检查点目录：

```text
US_LIST_JOB_DIR=/data/runtime/us-list-job
```

默认开发落点 `data-service/runtime/us-list-job/`，测试必须通过环境变量指向临时目录。`/data/runtime` 位于正式 `prisma-data` 命名卷，跨容器重建保留。

### 3.2 磁盘结构

```text
us-list-job/
  state.json
  generations/<snapshotId>/
    manifest.json
    pages/000001.json
    pages/000002.json
    ...
    candidate.json
```

- `state.json`：当前任务状态、当前 generation、下一次尝试时刻、最近错误、最近发布结果。
- `manifest.json`：`snapshotId/source/declaredCount/requiredPages/completedPages/createdAt/lastProgressAt/attemptsByPage/failuresByPage`。
- 页文件：页号、声明数、原始 `data`、完成时刻、内容 SHA-256。
- `candidate.json`：通过全部完整性验证的完整候选，只含可发布载荷和验证摘要，不含密钥。

写入顺序固定：

1. 页文件写 `.tmp`；
2. flush + fsync；
3. `os.replace` 原子改名；
4. 原子更新 `manifest.json`。

重启时按 manifest 与页文件哈希逐页核对；页已写而 manifest 未登记时验证后补登记；损坏或不符的页只重采该页。不能因为目录存在 JSON 就相信页已完成。

### 3.3 状态机

| 状态 | 含义 |
|---|---|
| `collecting` | 正在请求或处理页面 |
| `waiting` | 暂时退避，到 `nextAttemptAt` 自动继续 |
| `candidate_ready` | 完整候选已验证，尚未确认 Web 发布 |
| `publishing` | 正在调用 Web 发布 |
| `publish_unknown` | 发布结果未知，按 snapshotId 幂等重试 |
| `refreshing` | 已发布，正在刷新 us 行情 |
| `refresh_pending` | 名单已发布，行情刷新未收尾，自动重试 |
| `completed` | 名单已发布且 us 行情刷新完成 |
| `blocked` | 完整候选被本地保护闸拒绝，需新候选或人工决策 |

`waiting` 和 `publish_unknown` 不是失败；`blocked` 不允许无限重复提交同一份不合法候选。

### 3.4 单轮请求策略

保留：

- 单页超时 20s；
- 页间间隔 0.5s；
- 每页每轮最多 3 次；
- 首轮之外最多 2 轮集中修复；
- 集中修复换新 Session；
- 单轮突发上限 1500s。

1500s 降为**单轮突发上限**，不再是整任务最终期限。单轮达到上限、连续网络失败或仍有 pending 页时进入 `waiting`。

建议初值：

```text
US_LIST_JOB_RETRY_BASE_S = 60
US_LIST_JOB_RETRY_MAX_S = 600
US_LIST_JOB_NO_PROGRESS_S = 1800
```

退避 `60 → 120 → 300 → 600`，有成功页后重置；等待使用 `threading.Event.wait()`，服务关闭时可及时停止。

### 3.5 声明变化与穷尽页

任何页声明与首页不一致：旧 generation 标 `superseded`，新建 generation，从第 1 页重采，正式库不动。禁止跨声明拼页。

`requiredPages + 1` 空页证明也写入 generation；网络失败可稍后重试，非空或声明变化则候选不可发布。

### 3.6 观测

`/sync/status` 增加 `usListJob`：

```json
{
  "state": "collecting",
  "snapshotId": "...",
  "resolvedPages": 441,
  "requiredPages": 923,
  "pendingPages": 482,
  "lastProgressAt": "...",
  "nextAttemptAt": null,
  "lastError": {"kind": "network", "page": 442, "message": "..."},
  "lastPublishedSnapshotId": "...",
  "lastCompletedAt": "..."
}
```

只保留最近真实错误和聚合计数，不再产生数千条伪重试日志。

## 4. Provider 拆分

从 `akshare_provider.py` 拆出可复用单元：

- `request_us_page(page, session)`：单次 HTTP + JSONP 解析 + 页形状；
- `validate_us_candidate(generation)`：页义务、声明、去重、穷尽空页；
- `map_us_products(candidate)`：映射、行业筛选与 note。

保留 `_jsonp_payload`、`_us_expected_rows`、`_us_product`、`_us_page_count` 及既有完整性判据。`_list_us_stocks()` 不再自行翻完整份名单；它只返回当天已准备的完整候选，未准备好时由 `/products` 明确返回 `collecting`。

## 5. Web 幂等发布

### 5.1 新内部接口

```http
POST /api/sync/us-snapshot
x-write-token: ...
```

载荷包含 `snapshotId/count/products/source/acquisitionComplete/productPolicySubset/declaredCount/acquiredCount/note`。

服务端：

1. 校验写令牌和来源；
2. 校验 `snapshotId` 与完整性元数据；
3. 已成功发布过同一 `snapshotId` ⇒ 返回原成功结果；
4. 否则执行与现有 `syncType("us")` 相同的空载荷、70% 缩水、去重和事务发布；
5. 事务提交成功后才持久化发布记录。

发布记录落 Web 正式卷：

```text
/app/data/runtime/us-snapshot-publications.json
```

不能用模块内存代替，重启后必须识别重复回调。

### 5.2 抽取共用发布函数

从 `web/lib/sync.ts` 抽出 `publishProducts(type, data)`；现有 `_syncTypeInner()` 和新回调共用同一套保护与事务，禁止复制第二份闸门逻辑。

### 5.3 完成回调竞态

| 情况 | 处理 |
|---|---|
| Web 返回成功 | 标记已发布 |
| 明确拒绝完整性/缩水闸 | `blocked`，不无限重试同一载荷 |
| 连接失败/读超时 | `publish_unknown`，稍后用同一 snapshotId 重试 |
| DS 重启 | 从 candidate 与 snapshotId 继续 |
| Web 已提交但响应丢失 | 幂等重试返回原成功结果 |

“候选完整”和“正式库已发布”必须分账。

## 6. 每日同步与刷新解耦

### 6.1 `/api/sync` 不等待完整翻页

DS 调度仍按原顺序处理六类；当 us 任务尚未准备完成时，`/products?type=us` 返回 200 + `collecting:true`，Web 返回非失败结果：

```json
{"type":"us","collecting":true,"snapshotId":"...","progress":{"resolvedPages":441,"requiredPages":923}}
```

Web 整轮 `ok` 不把 `collecting` 当成功：`ok = results.every(r => !r.error && !r.collecting)`；DS `_execute` 新增 `outcome=collecting`，链式刷新只覆盖已收尾的五类。

### 6.2 刷新范围

普通轮在 us 尚未发布时请求：

```text
/api/market/refresh?types=stock,fund,bond,crypto,hk
```

us 发布后单独请求：

```text
/api/market/refresh?type=us
```

若 us 已在普通轮前发布，则普通轮可按原 `type=all` 刷新；同一轮只能有一个明确刷新 owner。

### 6.3 刷新进度按轮隔离

`refresh-progress.json` 增加 `runId` 与 `runs`，保留全局 `lastCompleted` 跨轮合并和当日幂等语义。健康视图与 DS 进度查询按当前 run 读取，us 独立刷新不得覆盖普通轮进度。

## 7. 备份与关闭

- 采集只写 `/data/runtime/us-list-job`，不写 SQLite，03:30 备份无需等待采集。
- `candidate_ready` 发布前检查备份是否运行；备份运行则等待。
- 发布事务与 SQLite 在线备份机制保证一致性；不为采集任务推迟或取消自然备份。
- 服务关闭时当前 HTTP 请求仍受 20s 上限；已确认页不丢，临时页文件重启验证后采用或重采；进程退出不记任务失败。

## 9. 验收判据

### 9.1 DS 离线

- 923 页分片保存，慢响应不触发整任务失败；
- 第 442 页达到单轮上限 → `waiting`，下一轮从 442 继续；
- 真实失败页经集中修复恢复；
- 重启只重采未确认页；
- 页文件已写、manifest 未写可恢复；
- 页文件损坏只重采该页；
- 声明变化新建 generation，不混页；
- 缺页、重复 symbol、短尾页、非空穷尽页不得生成 candidate；
- 连续 DNS/502/超时只增加退避，不删除已完成页；
- 单飞，不重复起 worker。

### 9.2 Web 离线

- 新回调复用 70% 缩水、空载荷、重复代码与事务保护；
- 同一 snapshotId 重试只发布一次；
- Web 重启后仍识别已发布代次；
- 响应丢失后重试不重复写库；
- 不合法候选零触碰正式 Product；
- us 独立刷新不覆盖普通轮进度；
- 普通轮不错误刷新尚未发布的旧 us。

### 9.3 故障注入

临时目录 + 临时数据库 + 合成 HTTP：

- DS 在 441/923 重启；
- Web 在发布前后分别重启；
- DS 发布响应丢失；
- 03:30 备份与 candidate_ready 同时发生；
- 完整任务只发布一次、只刷新一次；
- 中途正式表行数与 updatedAt 不变。

### 9.4 自然窗口

不人工 `POST /sync/run`。下一次 02:00 自动调度观察：

- 检查点持续增长，无整腿 deadline 批量补记；
- 最终完整发布并只刷新一次 us；
- 03:30 备份正常；
- 跨自然日已完成任务不再次购买整份名单；
- 失败旧记录保留，不改写。

- 不放宽任何完整性、缩水、冷却或重试闸门；
- 不删除旧容器、卷、恢复卷、备份或未跟踪现场；
- 不把 `waiting/blocked` 写成成功。

## 11. 执行结果（2026-11-26）

### 11.1 已落地

- **DS 持久化任务** `data-service/app/us_list_job.py`：`collecting/waiting/candidate_ready/publishing/publish_unknown/refreshing/refresh_pending/completed/blocked` 状态机；每成功一页先写 `.tmp`、flush + fsync、`os.replace`，再原子更新 `manifest.json`；重启按 manifest 与页文件 SHA-256 逐页核对，页已写而未登记时验证后补登记，损坏页只重采该页。声明漂移废弃旧 generation、从第 1 页重采；`requiredPages + 1` 空页证明也入 generation。退避 `60 → 120 → 300 → 600`，有成功页后重置；单飞、启动恢复、关闭可中断等待。
- **Provider 拆分** `akshare_provider.py`：新增 `request_us_page()`、`UsSnapshotChanged`、`validate_us_snapshot()`、`map_us_snapshot()`、`collect_us_snapshot()`；`_list_us_stocks()` 只消费已准备候选，未准备好抛 `ProviderCollecting`，不再在一次 HTTP 内翻 923 页。
- **DS 调度与观测**：`_execute` 普通轮改为 `?types=fund,stock,bond,crypto,hk`，五类收尾后启动/恢复 us 任务；新增 `outcome="collecting"`，`ok=None`，`collectingTypes=["us"]`，不写 `failedTypes`、不写 `completed`；`blocked` 仍落回真实失败。普通轮刷新请求带 `exclude=us&runId=daily-<北京日>`，us 发布后单独刷新 `?type=us&runId=us-<snapshotId>`。`/sync/status` 暴露 `usListJob`。
- **Web 幂等发布**：从 `web/lib/sync.ts` 抽出 `publishProducts(type, data)`，现有同步与新回调共用空载荷、70% 缩水、重复代码和事务保护。新增 `POST /api/sync/us-snapshot`，按 `snapshotId` 幂等；发布账本权威判据落在 SQLite 同事务表 `Product_snapshot_publication`（主键 `snapshotId`），JSON `/app/data/runtime/us-snapshot-publications.json` 仅作可观测副本。Web 已提交但响应丢失时，重试只回执、不重复写库。
- **collecting 语义**：`/api/sync` 新增 `?types=` 名单（`?type=` 优先），整轮 `ok = results.every(r => !r.error && !r.collecting)`；us 未就绪时返回 200 + `collecting:true` + `collectingTypes` + 说明，不是失败。`/products?type=us` 未就绪返回 200 + collecting，`blocked` 返回 502。
- **刷新进度按轮隔离**：`refresh-progress.json` 增加 `runId` 与 `runs[runId]`，保留全局 `lastCompleted` 跨轮合并和当日幂等；`/api/health?refreshRunId=...` 按轮读回，us 独立刷新不覆盖普通轮进度。
- **配置**：`docker-compose.yml` 增加 `US_LIST_JOB_DIR=/data/runtime/us-list-job` 与 `US_SNAPSHOT_PUBLICATIONS_FILE=/app/data/runtime/us-snapshot-publications.json`。
- **备份让位**：采集只写 `US_LIST_JOB_DIR`，不写 SQLite；发布与刷新是短事务，03:30 在线备份不需要等待慢采集。

### 11.2 与方案原文的差异（均已按更强判据实现）

1. 发布账本不是“只写 JSON”：权威判据改为 SQLite 同事务表，JSON 只是镜像。这样 Web 重启和“提交成功但响应丢失”都靠数据库判重，不依赖文件与事务的时序。
2. 刷新分流复用现有端点的 `?type=all&exclude=us`，不是方案草案里的 `?types=...`；`/api/sync` 才使用 `?types=`。两条腿的 URL 形状都已有测试钉住。
3. `collecting` 在 Web 整轮响应里表现为 `ok=false` + `collecting=true`：它不是成功，也不是失败；DS 按 `collecting` 分支记 `outcome="collecting"`，不会把 `ok=false` 误判成 `partial_failed`。
4. 新增 `us-snapshot` 内部路由、发布账本表、`refreshRunId` 读取和 `runId/runs` 隔离，均比草案多一层可验证状态位；未放宽任何既有闸门。
