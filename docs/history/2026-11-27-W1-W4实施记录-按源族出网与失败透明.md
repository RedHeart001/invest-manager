## 2. W1：海外源按源代理、国内源强制直连

### 2.1 为什么不能只靠 `NO_PROXY`

11-27 探针（两次都是同一枚代理 `127.0.0.1:7897`）：

| 目标 | 直连 | 套代理 |
|---|---|---|
| `push2.eastmoney.com` | HTTP 200／3518ms | **`ProxyError`** |
| CoinGecko | 通 | 通 |
| Tavily | 通 | 通 |
| `api.deepseek.com` | 401（未带 key，属正常） | 401 |

⇒ 国内源一旦被代理就从可用变不可用；海外源没有明确收益也没有明确损失。而 `main.py:12` 的 `NO_PROXY=*` 是 `setdefault`，容器里 compose 显式传入的 `NO_PROXY` 只有 `127.0.0.1,localhost,::1`（不含 `web`／`data-service`），所以：

- 不能设全局代理（`POST http://web:3000/api/sync` 这类容器内调用会被拦）；
- 不能拿 `NO_PROXY` 是否写全当唯一防线。

### 2.2 唯一收敛点

新增 `data-service/app/utils/http.py`，两个出口语义互斥：

| 函数 | 返回 | 用途 |
|---|---|---|
| `direct_proxies()` | `{"http": None, "https": None}` | 国内源与容器内调用的 `proxies=` 实参 |
| `overseas_proxies()` | 配了就有、**没配是 `None`**（不是空字典、不虚构地址） | 海外源 |
| `overseas_session()` | `trust_env=False` 的共享会话，配了代理就设上 | 海外源（`NO_PROXY=*` 之下只有它能生效） |
| `reset_overseas_session()` | — | 测试／配置变更后重建 |
| `direct_session(requests_module)` | 每次**新建**的直连会话 | 国内源翻页（"换一枚会话重试"那条恢复路径靠它不复用） |

**这是本仓唯一一处"看着能简化、实际会静默失效"的写法**：`requests` 的 `merge_environment_settings` 对 env 代理用 `proxies.setdefault(k, v)`，只有键**已存在且值为 None** 才能压住。已在 `requests 2.34.2` 实测：

- 传 `{}` ⇒ 得到含代理的 `OrderedDict({'https': ..., 'http': ...})`（被 env 填回）；
- 传 `{"http": None, "https": None}` ⇒ 得到空 `OrderedDict`。

`test_w1_http_egress.py` 用**真 env ＋ 真 `merge_environment_settings`** 反锁这一点，不去 mock requests 的内部函数。

## 4. W3：每日最多一次有界补试

### 4.1 常量与状态机（`sync_scheduler.py`）

| 名字 | 值 | 含义 |
|---|---|---|
| `RETRY_TRIGGER` | `"daily-retry"` | 补试轮自己的 trigger（不是自然轮） |
| `RETRY_DELAY_S` | `30 * 60` | 失败后延迟 30 分钟 |
| `RETRY_MAX_ATTEMPTS` | `1` | 每日最多补一次 |
| `RETRY_WAIT_INTERVAL_S` / `RETRY_WAIT_MAX` | `60.0` / `10` | 主任务在跑时最多让位 10 分钟 |
| `RETRY_EXCLUDED_TYPES` | `("us",)` | us 由持久化任务自行续跑，不补 |
| `RETRY_STATES` | `pending`/`running`/`completed`/`exhausted`/`cancelled` | 五态 |

函数：`retry_state`／`_write_retry`／`_plan_retry`／`_transition_retry`／`_retry_types_from`／`_claim_for_retry`／`_retry_worker`／`_schedule_retry`／`_mark_retry_outcome`／`_resume_retry_after_start`；`_execute` 拆成薄包装 ＋ `_execute_types`；`_refresh_leg` 支持 `types=`；`status()` 新增 `retry`／`retryLastResult`／`retryLastRefresh`；`start_scheduler()` 挂 `sync-retry-resume`。

### 4.2 边界（`test_w3_retry.py` 83/83 逐条钉住）

只对 `trigger == "daily"` 的 `partial_failed` 登记；延迟 30 分钟；**不带 `force`**（仍受 web 当日幂等闸门约束）；`us` 排除。

| 情形 | 行为 |
|---|---|
| `inconclusive`（回调读超时） | **不补**——结果未知时重跑，把额度花在可能已成功的一轮上 |
| `rejected`／`failed`／`collecting`／`skipped`／`completed` | 不补 |
| 主任务 `running` | 让位，等 10 分钟仍不空则记 `cancelled`，**绝不叠第二条腿**，也不放开主任务的 running 锁 |
| 跨日 pending | 记 `cancelled`（`not today`），不在今天补昨天 |
| 补试仍失败 | `exhausted`，当日不再自动执行 |

### 4.3 账分离（最容易被日后改动破坏的一处）

补试轮**不改写** marker 的 `lastAttempt*`／`lastResult`／`runs`：

- `lastAttemptTrigger` 必须仍是 `daily`，否则重启补跑判据与 `legStaleness` 会把账算错一天；
- `runs` 的语义是"本进程跑了几轮整轮"，补试不该 +1；
- 补试结果只写 `retry` 计划与 `retryLastResult`；
- `_mark_attempt`／`_mark_outcome` 覆写时必须把 `retry` 键**原样带过去**（否则 02:10 一次手动补跑会把 02:30 排好的补试静默吃掉）。

刷新腿只覆盖本轮类型：`exclude` 剔掉其余四类、`runId=retry-<today>`（不与自然轮的 `daily-<today>` 共用同一份进度文件）；自然轮那条腿一字未变（`exclude=us`、`runId=daily-<today>`）。

## 5. W4：四态展示

### 5.1 判据分两侧

方案要的四态是 `fresh`／`degraded`／`stale`／`unavailable`（`fresh` 不出字），实现层落到 `StaleNote["kind"]` 六档，因为**判据来自两侧**：

- **今日同步结果这一侧**（`sync-state.json`，W4 新增读取）：`failed`、`degraded`、`unavailable`；
- **库内新鲜度这一侧**（原有三档，一条都不改判）：`list`、`pending`、`snapshot`。

优先级：`failed` ＞ `degraded` ＞ `list` ＞ `pending` ＞ `snapshot`，同一类只报一条。

`failed` 这一档治的正是"昨天成功、今天 02:00 失败"——旧判据只看库里有多旧，于是那一整天页面都把昨天的名单当今天的用，一句提示都没有。而 `skipped`（当日幂等闸门挡下）**不是失败**，不产生说明；今日还没跑（盘上还是昨天那轮）时这一侧一个字都不出，不能把昨天那轮说成"今日失败"。

### 5.2 改动落点

- 新增 `web/lib/sync-state.ts`：**零出网**读 DS 共享卷 `sync-state.json`，候选路径 env → `/app/data/runtime/` → 仓库 `data-service/runtime/`。导出 `readSyncAttempt`／`parseSyncAttempt`／`todayFailure`／`todayDegradedNote`／`retryNote`／`DEGRADED_NOTE_MARKER`。
- `web/lib/freshness.ts`：`StaleNote` 扩到六档并加 `dataAt`／`reason`／`retry`；`staleNotes(rows, today, attempt)` 加第三参。

- `web/lib/browse.ts` 传 `readSyncAttempt()`，`stale.slice(0,2)` ＋ `staleMore` 一并说出"还有几条"。

### 5.3 实施中修正的两处自身偏差

1. `todayFailure`／`todayDegradedNote`／`retryNote` 都接受**显式 `today`**（由 `staleNotes` 传下去）。否则跨零点的一次渲染会在两处用不同的"今天"。
2. `degraded` 但库里零行时降级成 `unavailable`——不能说"今日已更新"，那与事实相反。

## 6. 实现过程中自己造成并修正的三处缺陷

> 这一节是本文的主要价值。三处都不是"测试写错了"，前两处是真实代码缺陷，第三处是用法册（测试）证据不足。

### 6.1 `direct_session()` 绕过了离线套件的替身（真实缺陷）

**现象**：`test_cr9_59_us_list.py` 首次全量跑就红，报 `us list page budget 1 < required 923`。

**根因**：`direct_session()` 住在 `utils/http.py`，里面直接用本模块的 `requests`。而离线套件换的是 `akp.requests`／`us_list_job.requests`（模块级名字）⇒ 换成 `direct_session()` 之后，那句号称"零出网"的翻页用例**真的打到了新浪**，一路要到 923 页的预算才因为 `US_LIST_PAGES` 的上限报错。

**这不是测试的问题**：套件用模块级替身是既有约定，W1 打破了这个可测性契约。如果当时顺手改测试（给 `http.py` 也打补丁），就等于把"零出网"这个前提偷偷改掉。

**修法**：`direct_session(requests_module=None)`，由调用方传自己模块的 `requests`；四个调用点改成 `direct_session(requests)`；`test_w1_http_egress.py` 加 `[8b]` 反向锁——`providers/akshare_provider.py` 与 `us_list_job.py` 里**不许出现裸 `direct_session()`**。

### 6.2 补试仍失败时，落盘的 `note` 是整轮语境（真实缺陷）

`failed` 分支那句 note 是**整轮**语境的（"lastDate 已置位，本轮不自动重试"）。在补试轮里它自相矛盾——这一轮本身就是那次重试——而且不含任何一类的错误原文，盘上只剩一句"失败"。

**修法**：补试分支按自己的语境改写 note，点名补了谁、为什么还失败（逐类 `type: error`，截断 300 字）、以及"今日不再自动重试；旧数据保留，确要重跑走 `POST /sync/run?force=true`"；`inconclusive` 另有一句（"web 侧可能仍在写，请查 `Product.updatedAt`／`snapshotAt`"）。

### 6.3 `[5b]` 用例用后台线程放锁（竞态写法）

`test_w3_retry.py` 的 `[5b]`（"让位是有终点的"）起初用后台线程在若干次 `sleep(0)` 后放开 `running`。第一轮全量门禁就偶发红 1 枚（"主任务收尾后认领成功"）——线程抢不到 GIL 时主任务还没放锁，等待窗口就用完了。

**修法**：改成在 `time.sleep` 的替身里按调用次数放锁，次序完全确定；连跑 5 次全 exit=0。

**教训**：偶发红不是噪声，是这条用例自己没把时序钉死。用后台线程去驱动被测函数的等待循环，等于把判据交给调度器。

### 6.4 一处测试替身随实现更新（非缺陷，但改的是旧用例）

`test_cr9_95_hotspot_marker.py` 的 `_WebQuery` 替身原先签名 `__call__(self, url, params=None, timeout=None)`。W1 给 `_catch_up_decide` 的 web 回查加了 `proxies=direct_proxies()` ⇒ 替身不再接得住，`_catch_up_decide` 整条判据失真。改为收下 `**kw` 并留存一份 `proxies_seen` 证据，22/22 恢复。
