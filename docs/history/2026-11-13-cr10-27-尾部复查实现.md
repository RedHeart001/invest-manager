## 二、实现（web/lib/kline.ts，三处）

1. **尾部条件与起点**：`maxCached < end` → `maxCached <= end`（:360）；回源起点 `isoAddDays(maxCached, 1)` → `maxCached`——含缓存末日，未完结 bar 有修正路径。
2. **限定更新**：`upsertCandles` 新增 `refreshExisting` 模式（仅尾部复查路径传 true）——SQL 用 `INSERT … ON CONFLICT("type","code","date") DO UPDATE SET open/high/low/close/volume/source=excluded.*`（:228），冲突行保留原 id；头补/整段回源维持 `INSERT OR IGNORE`（:231）只写新日期。**不无差别重写历史**：更新面由取数窗口（缓存末日→请求末日）限定。唯一键、毫秒整数日期（`dayStart().getTime()`）、50 行分块均保留。
3. **同日复查顺延**：头部本请求已回源（`headFetchAttempted`，:340）且尾部无新日（`maxCached === end`）时，同日复查顺延一个窗口——写 `lastCheckedTail`（:369）＋如实 note「本次已回源头部缺口，尾部同日复查顺延一个窗口」。尾部有新日时不受影响（CR-05 头不压制尾保留）。
   - **为什么顺延**：既有钉子 `kline-headtail.test.ts`「仅头缺口、无尾缺口时只回头部一次」与红测窗口用例（两请求合计 1 次回源）共同要求头部已回源时同日复查不得另发一次。
   - **已知边界（诚实记账）**：头缺口持续存在的标的（如上市不足区间），同日修正会被持续顺延——主场景（缓存齐全的细节页重访）不受影响。
4. **fetchedDays 语义**：被更新的尾部行计入 fetchedDays（红测用例 1 钉住 =1）；cachedDays = rows.length - fetched 随之自洽。
