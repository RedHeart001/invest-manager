# 项目规则（Invest Manager）

> 本文件由项目根 `CLAUDE.md` 通过 `@.claude/rules/project.md` 导入，**每次会话都会加载**，不要加 `paths:` frontmatter
> （加了就只在处理匹配文件时才加载，而提交纪律必须每次都生效）。

## 密钥：绝对禁令

**绝不允许把主人的任何密钥 / 凭据提交进仓库。** 没有例外——不存在"这个看起来不像密钥"的自行判断，也不存在"就提交这一次"。
一旦进入 git 历史，即使随后删除，凭据也已存在于每一个克隆中，必须当作**已泄露**处理。

### 本项目视为密钥的东西（出现即不得提交）

| 类别 | 具体项 |
|---|---|
| LLM | `LLM_API_KEY`；`LLM_BASE_URL` 中的真实私有端点 |
| 数据源 | `TAVILY_API_KEY` / `SEARCH_API_KEY`（Tavily）、`ALPHA_VANTAGE_API_KEY` |
| 落库回调 | `INGEST_TOKEN` |
| 基础设施 | 真实代理凭据、含口令的数据库连接串、SSH 私钥、证书 |
| 形态特征 | `sk-…`、`tvly-…`、`ghp_…`、`AKIA…`、以及赋给 `*_KEY/_SECRET/_TOKEN/_PASSWORD` 的长随机串 |

### 禁止 add 的文件（即便它们没被 gitignore 覆盖）

- `.env`、`.env.local`、`.env.*.local` —— 任何**真实环境变量文件**
- `*.db`、`*.db-wal`、`*.db-shm`（含真实业务数据）
- `backups/` 下的任何文件
- `*.pem`、`*.key`、`*.p12`、`id_rsa*`
- `.claude/settings.local.json` 等本地配置

> ✅ **唯一可以提交的是模板**：`.env.example` / `web/.env.example`，且其中密钥类取值**必须为空**。
> 若发现模板里被填了真值，停下报告，**不要自行改动主人的配置文件**。

### 提交前的强制自查

每次 `git add` 之后、`git commit` 之前，**必须**跑这两条：

```bash
git diff --cached --name-only                                              # 清单里有禁止文件吗
git diff --cached | grep -iE '(sk-|tvly-|ghp_|AKIA)[A-Za-z0-9_-]{10,}'     # 暂存内容里有密钥形态的字串吗
```

两条都干净才提交。**绝不用 `git commit --no-verify` / `-n` 绕过检查。**

### 发现有密钥时

- **尚未提交**：立即 `git restore --staged <file>` 撤出暂存，停下报告。**不要自行删除或改写主人的 `.env`**。
- **已经提交**：**立即停下如实报告**。不自行改写历史、不自行 force push——历史重写与远端写入同属不可逆操作，必须由主人决定。
  同时提醒主人：该凭据应视为已泄露，需**到服务方轮换**，而不只是从代码里删掉。

## 提交纪律

**本项目已授予常驻授权**：凡是主人让我改动了项目文件，**改动完成后主动 `git add` + `git commit`，不再逐次询问**。
（这覆盖默认的"commit 需逐次明确授权"——但**仅限本项目、仅限本规则描述的范围**。）

### add 的范围

- **只 add 我本次改动涉及的具体文件**——逐个列路径，或 add 明确到本次改动的目录。
- **禁止 `git add -A` / `git add .` / `git add -u`**。本仓库长期存在大量未提交的在制工作
  （例如 CR6 那轮遗留的约 84 个路径），无差别 add 会把不同源的改动混进同一条提交，事后 blame 不出来。
- add 前用 `git status --porcelain` 核对清单，确认里面没有我没碰过的文件。

### 什么时候触发

- **任何让我改动文件的指令都算**：代码、文档、配置、`.env.example`、技能定义等一律适用。
- 只读任务（分析、审查、答疑、给方案）**不触发**——哪怕我在里面读了很多文件。
- 没有实际文件变化时**跳过**，不制造空提交。

### commit message

- **标题一句话**说清本次改了什么，沿用本仓库既有的 Conventional Commits + 中文风格：
  `fix:` / `feat:` / `docs:` / `chore:` / `refactor:`，必要时带 scope（如 `docs(memory):`）。
- 例：`docs: 文档重组，PLAN/Progress 迁入 docs/ 并拆出 CONSTRAINTS/CODE-REVIEW/FIX-LEDGER`
- **默认只写标题**。仅当改动跨多个文件、或包含"不看就说清"的非显然变化（如修正了一个错误结论、重建了缺失记录）时，
  才补一个短 body，且不超过 5 行。
- 不要写"按用户要求修改"这类无信息量的描述——要让半年后的自己看懂改了什么、为什么。

### 边界

- **只 commit，不 push**。推送、合并、rebase、发布仍需主人单独授权。
- **密钥绝对禁令见本文档开头的「密钥：绝对禁令」节**——它是本项目优先级最高的约束，任何提交动作前先过那一节的自查。
- **若当前在默认分支 `master`**：停下来先问，不要直接在 master 上提交。本项目日常开发分支是 `dev`。
- **提交失败时**（pre-commit 拦截、无实际变更等）：如实报告失败原因，**不要为了让提交通过而改命令绕过**。

## 项目文档结构

改代码前先看约束，改完按上文提交。

| 文件 | 什么时候看 |
|---|---|
| `docs/PLAN.md` | 需求与设计的**唯一来源**——要改行为先看这里是否已定稿 |
| `docs/CONSTRAINTS.md` | **改代码前必自查**：C1–C34 不得回退的约束、跨服务契约坑、数据源事实、部署约束 |
| `docs/PROGRESS.md` | 唯一的进度账本——完成一个阶段/里程碑时更新它 |
| `docs/CODE-REVIEW.md` | 各轮审查发现了什么（只增不改）；提新发现前先查文末的「已核验排除的误报」 |
| `docs/FIX-LEDGER.md` | 每项修了没、怎么验的；**未闭环看板置顶** |
| `docs/history/` | 归档：逐项做法、改动文件清单、一次性操作记录 |

## 其他长期有效的纪律

（不在此重复正文，以来源为准）

- **测试失败最多重试 3 次**，仍失败即停止并沟通，不无限重试（`docs/PLAN.md` R9）。
- **开发期间不在 `next dev` 运行时执行 `npm run build`**（类型检查用 `npx tsc --noEmit`）——
  已因此踩过 dev/build 冲突导致页面只剩骨架的坑。
- **修"失败负缓存 / 限流计数 / 熔断计数 / 复查窗口"类问题时必须附反向验证**
  （临时回退修复 → 确认断言精确失败 → 恢复），这是 C34 的验收要求。
