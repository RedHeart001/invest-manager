# 项目规则（Invest Manager）

> 本文件由项目根 `CLAUDE.md` 通过 `@.claude/rules/project.md` 导入，**每次会话都会加载**，不要加 `paths:` frontmatter
> （加了就只在处理匹配文件时才加载，而提交纪律必须每次都生效）。

## 密钥：绝对禁令

**绝不允许把主人的任何密钥 / 凭据提交进仓库。** 没有例外——不存在"这个看起来不像密钥"的自行判断，也不存在"就提交这一次"。
一旦进入 git 历史，即使随后删除，凭据也已存在于每一个克隆中，必须当作**已泄露**处理。

### 本项目视为密钥的东西（出现即不得提交）

| 类别 | 具体项 |
|---|---|
| LLM | `LLM_API_KEY`；`LLM_BASE_URL` 中的真实私有端点 |
| 数据源 | `TAVILY_API_KEY` / `SEARCH_API_KEY`（Tavily） |
| 落库回调 | `INGEST_TOKEN` |
| 基础设施 | 真实代理凭据、含口令的数据库连接串、SSH 私钥、证书 |
| 形态特征 | `sk-…`、`tvly-…`、`ghp_…`、`AKIA…`、以及赋给 `*_KEY/_SECRET/_TOKEN/_PASSWORD` 的长随机串 |

### 禁止 add 的文件（即便它们没被 gitignore 覆盖）

- `.env`、`.env.local`、`.env.*.local` —— 任何**真实环境变量文件**
- `*.db`、`*.db-wal`、`*.db-shm`（含真实业务数据）
- `backups/` 下的任何文件
- `*.pem`、`*.key`、`*.p12`、`id_rsa*`
- `.claude/settings.local.json` 等本地配置

> ✅ **唯一可以提交的是模板**：`.env.example` / `web/.env.example`，且其中密钥类取值**必须为空**。
> 若发现模板里被填了真值，停下报告，**不要自行改动主人的配置文件**。

### 提交前的强制自查

每次 `git add` 之后、`git commit` 之前，**必须**跑这两条：

```bash
git diff --cached --name-only                                              # 清单里有禁止文件吗
git diff --cached | grep -iE '(sk-|tvly-|ghp_|AKIA)[A-Za-z0-9_-]{10,}'     # 暂存内容里有密钥形态的字串吗
```

两条都干净才提交。**绝不用 `git commit --no-verify` / `-n` 绕过检查。**

### 发现有密钥时

- **尚未提交**：立即 `git restore --staged <file>` 撤出暂存，停下报告。**不要自行删除或改写主人的 `.env`**。
- **已经提交**：**立即停下如实报告**。不自行改写历史、不自行 force push——历史重写与远端写入同属不可逆操作，必须由主人决定。
  同时提醒主人：该凭据应视为已泄露，需**到服务方轮换**，而不只是从代码里删掉。

## 提交纪律

**本项目已授予常驻授权**：凡是主人让我改动了项目文件，**改动完成后主动 `git add` + `git commit`，不再逐次询问**。
（这覆盖默认的"commit 需逐次明确授权"——但**仅限本项目、仅限本规则描述的范围**。）

### add 的范围

- **只 add 我本次改动涉及的具体文件**——逐个列路径，或 add 明确到本次改动的目录。
- **禁止 `git add -A` / `git add .` / `git add -u`**。本仓库长期存在大量未提交的在制工作
  （例如 CR6 那轮遗留的约 84 个路径），无差别 add 会把不同源的改动混进同一条提交，事后 blame 不出来。
- add 前用 `git status --porcelain` 核对清单，确认里面没有我没碰过的文件。

### 什么时候触发

- **任何让我改动文件的指令都算**：代码、文档、配置、`.env.example`、技能定义等一律适用。
- 只读任务（分析、审查、答疑、给方案）**不触发**——哪怕我在里面读了很多文件。
- 没有实际文件变化时**跳过**，不制造空提交。

### commit message

- **标题一句话**说清本次改了什么，沿用本仓库既有的 Conventional Commits + 中文风格：
  `fix:` / `feat:` / `docs:` / `chore:` / `refactor:`，必要时带 scope（如 `docs(memory):`）。
- 例：`docs: 文档重组，PLAN/Progress 迁入 docs/ 并拆出 CONSTRAINTS/CODE-REVIEW/FIX-LEDGER`
- **默认只写标题**。仅当改动跨多个文件、或包含"不看就说清"的非显然变化（如修正了一个错误结论、重建了缺失记录）时，
  才补一个短 body，且不超过 5 行。
- 不要写"按用户要求修改"这类无信息量的描述——要让半年后的自己看懂改了什么、为什么。

### 边界

- **只 commit，不 push**。推送、合并、rebase、发布仍需主人单独授权。
- **密钥绝对禁令见本文档开头的「密钥：绝对禁令」节**——它是本项目优先级最高的约束，任何提交动作前先过那一节的自查。
- **若当前在默认分支 `master`**：停下来先问，不要直接在 master 上提交。本项目日常开发分支是 `dev`。
- **提交失败时**（pre-commit 拦截、无实际变更等）：如实报告失败原因，**不要为了让提交通过而改命令绕过**。

### docs 结构标准（2026-10-08 立）

**三层结构**：
1. **统一入口**（`docs/README.md`）：项目是什么、当前状态（随 FIX-LEDGER 同步）、文档地图（要 X → 读 Y）、常用命令、历史在哪
2. **活跃工作区**（PLAN/CONSTRAINTS/FIX-LEDGER）：当前轮次的完整上下文，保持现状
3. **历史档案**（`docs/history/`）：被压缩的过程材料 ＋ **前向任务书**（见「写：讨论产出的落点」表那一行），按主题命名（日期 + 主题），README.md 索引保持更新

**精简标准**：
- **PROGRESS.md**：从"进度账本"变成"状态总览"——日志整体归档到 `docs/history/`，主文件只保留状态总览（P0–P7）+ 阻塞与问题（已闭环项一行结论+指针，进行中项完整说明）
- **CODE-REVIEW.md**：从"档案馆"变成"当前轮发现 + 误报索引"——已闭环轮次的发现原文归档到 `docs/history/`，主文件只保留**当前开放轮次**的完整发现 + 误报排除表（11-03 改：原句钉死「当前轮 CR9」＝那格后来漂了十几天，轮次号一律不在此处复述，取号权威＝FIX-LEDGER 状态卡）
- **PLAN.md**：决策记录中过时的决策必须有"⚠️ 已作废/已执行/已被推翻"标注
- **FIX-LEDGER.md**：状态卡 + 未闭环看板 + 待拍板 + CR9/CR8 计划，已闭环条目归档到 `docs/history/`

**后续更新约定**：
- 每次轮次推进、未闭环项增减、待拍板变化时，**同步更新 `docs/README.md` 的"当前状态"节**（与 FIX-LEDGER 看板一致）
- 被压缩的过程材料一律进 `docs/history/`，并在 `history/README.md` 加索引行
- 同一事实只有一个"家"，不写第二处
- **可复算数字必须带日期＋出处（2026-10-08 立）**：凡把**行号、套件数、断言数、库内行数、桶读数**这类能从代码／回执／库里现查的数抄进正文，同一句里必须给出**日期＋出处**（回执文件名／命令／`path:line`）；**不带出处的裸计数不许进正文**，给不出出处就改写成"用这条命令现查"而不是写一个数。权威计数只住在 `docs/FIX-LEDGER.md`「验证门槛（权威现值）」，其他文件只留指针。

### docs 体量治理（2026-10-09 立；主人的字＝「我认可你的方案，并把这个浓缩成规则，更新到 .claude/rules/project.md 里面」）

**这条规则只解决一件事：让活跃工作区的文件不至于长成读不动的样子。报警自动做，搬动等主人给字。**

**报警器（每轮收尾跑一次，零出网，只做这一件）**
- 执行件＝`python scripts/docs-scan.py`（一条命令同时出：体量三读数＋断链扫描；断链非 0 时退出码=1）；自检＝`python scripts/docs-scan.py --selftest`（**全绿**——判据条数随执行件演进而变，不在此钉一个静态数）。
- 三把尺，任一超标就在收尾报告里点名（文件／节／行＋当轮读数与出处）：单文件 > **120,000 字符**（**例外：`docs/CODE-REVIEW.md` 给 150,000**——它是"一轮一节"的发现记录，852 行、零巨行、结构健康，用同一个数只会逼着把完好的整节拆出去、反而破坏阅读连续性；账本类 `FIX-LEDGER` 维持 120,000，逼它搬）；单行 > **1,000 字符**；单节（一个标题到下一个**同级或更高级**标题）> **30,000 字符**。
  - **「节」按两把读数取并集：叶节 ∪ 容器自身体**（口径恒等式＝自身体＋Σ直接子节＝跨度，不重复计数）。只按终端叶节会把挂在容器**自身体**上的最大一块设成不可见（10-10 实测：门槛堆积 124,333 挂在 `## CR9 · 修复计划` 自身上＝L390→首个子节 L435，不是叶节）。
  - **单行阈 1,500→1,000 的理由（10-22 实测）**：1,500 时 `FIX-LEDGER` 只有 1 条命中且卡在 1,488 刚好阈下，而它实际有 **18 行 >1,200、31 行 >1,000**——旧尺量不到真正读不动的行。降到 1,000 后 `CODE-REVIEW`（852 行、零巨行）**一行都不会被误伤**，定位是准的。
- **行数不作闸**（10-09 实测：`FIX-LEDGER.md` 495 行／321,975 字符读不动却不触发，`CODE-REVIEW.md` 1,102 行／125,023 字符结构正常反而触发）。
- **报警读数按轮次记，带时刻与出处，不在正文钉一个静态数**——落账这个动作本身会推进它（同一晚两小时内 495→500 行、321,975→331,485 字符）。
- 范围＝活跃工作区（`docs/*.md`）；`docs/history/` 不触发（归档区继续长是正常态，规则若不排除它会自噬）。

**动作＝「搬」＋「现值块重写」两种（后者的定义、四个具名块与三道硬闸见文末「docs 现值块与压缩」节）；正文（发现原文／判据本体／沿革）仍然只增不改**
- 超标且**已闭环**的整节：标题＋正文一字不改搬进 `docs/history/`＋原地留一行指针＋`history/README.md` 加索引行——沿用上面「被压缩的过程材料一律进 `docs/history/`」那条，不新造动作。
- **不许**为缩体量重写、删句、合并历史原文（撞「只增不改」）；表格行里的巨段要搬，得整段挪进同文件的小节并在行内留指针，不许断行改字节。
- **写长行的禁令：不许再把「本体＋沿革」压进同一行（10-22 立，主人的字＝「后续不能再出现」）**。这是 `FIX-LEDGER` 长成读不动的**唯一成因**——它不是被搬出来的，是被一行一行写出来的（10-22 实测：31 条 >1,000 字符的行里 28 条是这种写法）。三条硬要求：
  1. **一个转折就换行**。写完一句「现值 X」若要接「原先是 Y／后来改成 Z」，**另起一行写 `> `**，不要用逗号或分号接在同一行里。
  2. **写之前先估长**。一个新段落若要写超过约 600 字符，就拆成多行 `> `（CommonMark 里相邻 `> ` 行仍是同一段落，**渲染与语义都不变**）。
  3. **断行只在句读标点之后**（`。；！？`），且**不删一个字**——判据是可证伪的：把插入的 `\n> ` 去掉后必须逐字还原原文；另跑一遍「去 `>` 与换行后的字符多重集相等」。
- **承认存在的例外（10-22 主人拍板：不能拆的就承认它们存在）**：**表格行**不许断行（`|` 是列分隔符，一断就错位）⇒ 现存的 3 条 >1,000 字符的表格行（`FIX-LEDGER` 的 CR9-26／CR9-41 看板行与 OPT-4 候选行）**作为已知例外留在报警里，不追求清零**；但它们同样适用上面的禁令：**新写的表格单元格不许再塞长沿革**，要写就写进表格下方的注、行内只留一句现值＋指针。
- **例外：「状态卡／速览」类明细允许整段进 `history/`**（10-11 补）。上一条要求「挪进同文件小节」照办会把明细继续堆在活跃区、与本规则初衷相反；状态卡里的出网账、门禁读数、轮次计数等正是「被压缩的过程材料」，本就该进归档。⇒ 这一类可整段搬进 `docs/history/`，沿用同一道 `--move` 闸。
- **搬动要主人单给一句字**，一轮一批；自动化到此为止（只报警）。
- **搬运动作只能由执行件做**：任何搬动（整节搬进 history、文件内换序、区间搬）都走 `scripts/docs-scan.py` 的 `--move` 四种切块，不再手写搬家脚本。#61 首搬事故（10-10）＝手写脚本按「下一个 `####`」划节、而本规则 :131 写的是「下一个同级或更高级标题」，把 `## 附录` 56 行一起搬走——错在**范围**而非无损性，正是"手写脚本没有拦范围的闸"这一形。
- **文件内换序与搬进 history 纳入同一道闸**：同一枚 `--move` 越界拒绝判据（被搬块内每枚标题的完整跨度须落块内）＋同一套无损证明；换序额外验缝（不得造出 `---` 紧贴段落行的 setext 下划线形，允许随块带一枚相邻空行）。
- **执行件不受自身尺约束**：`scripts/docs-scan.py` 自身的体积／行长不触发报警（它不在 `docs/` 范围内）。
- 搬完必跑**断链扫描**：正文里每个「见第 N 项」「追加N」都要能解析到盘上位置或指针行。10-08 那次搬家留下 85 处断链＝没有这一半的代价。

### 写：讨论产出的落点（常驻设定）

**与主人讨论需求、设计、项目优化时，把沟通记录精炼后写进对应文件**，不让结论只留在对话里。
按下面路由落笔，不另开新文件、不跨文件重复同一结论。

| 讨论产出了什么 | 落到哪 | 写成什么形态 |
|---|---|---|
| 新需求 / 需求变更 / 设计选型 | `docs/PLAN.md` | 需求条目（R/M 编号）或「决策记录」一行：结论 + 日期 + 理由 |
| 「这块以后不能碰」——踩到的坑、跨服务契约、数据源事实 | `docs/CONSTRAINTS.md` | C 条目或 §B/§C 契约坑：现象 + 为什么 + 正确做法 |
| 一个阶段/里程碑做完、验收通过 | `docs/PROGRESS.md` | 日期日志一行（做了什么 / 结论 / 验证）+ 更新状态总览 |
| 发现了问题，但还没定怎么修 | `docs/CODE-REVIEW.md` | 追加条目（**只增不改**）：现象 + 证据 + 复现命令 |
| 问题修了 / 决定不修 / 验证证据 | `docs/FIX-LEDGER.md` | 未闭环看板增删 + 执行记录（编号 / 处置 / 证据 / commit） |
| 一次性操作过程、被压缩掉的明细；**前向任务书**（排给未来窗口、**尚未执行**的一次性任务书） | `docs/history/` | 新建 `<日期>-<轮次或主题>.md` + 在 `history/README.md` 加索引行；**前向任务书另须由索引行标生命周期**（执行前通读 → 执行完转标「已执行，勿再执行」），本体仍按「只增不改」 |

### 沉淀到哪一层：纪律 / 禁区

讨论出的"以后该怎么做"按复杂度分两层，**别错层**：

| 形态 | 判据 | 落到哪 |
|---|---|---|
| **纪律** | 一句话能说清 | 本文件「其他长期有效的纪律」节 |
| **禁区** | "不许碰"——不得回退的约束、契约坑、数据源事实 | `docs/CONSTRAINTS.md` |

多步骤做法若够格沉淀，按上面两层择一落笔。

### 落笔纪律

- **落笔时机与主动提醒**：讨论过程中**不动文件**，等结论成形再一次性落笔；讨论中主人明确拍板的事项则立刻落。
  **每次沟通收尾时主动问一句「是否要记一下？」**——不要默默略过，也不要未经确认就往文档里写。
- **只落结论，不落聊天**。方案比选、探索性问答、被推翻的中间想法**不写**；只有有长期价值的单一结论才落。
- **没拍板的标「待拍板」**，不写成正文。讨论中的选项放 `FIX-LEDGER.md` 看板的待决策区或 `PLAN.md` 决策记录的待定节，等主人明确后再升级为正文。
- **不臆测**。写进去的每条状态都要能由一条命令、一个测试或一份代码复现；写不出就标 ⏳ 待核。
- **落笔即提交**：写完按上文「提交纪律」add + commit，只 add 本次写到的文档。
- `docs/history/` 与 `CODE-REVIEW.md` **只增不改**；状态只在 `PROGRESS.md` / `FIX-LEDGER.md` 维护，归档里不写"最新状态"。

## 其他长期有效的纪律

（不在此重复正文，以来源为准）

- **测试失败最多重试 3 次**，仍失败即停止并沟通，不无限重试（`docs/PLAN.md` R9）。
- **开发期间不在 `next dev` 运行时执行 `npm run build`**（类型检查用 `npx tsc --noEmit`）——
  已因此踩过 dev/build 冲突导致页面只剩骨架的坑。
- **修"失败负缓存 / 限流计数 / 熔断计数 / 复查窗口"类问题时必须附反向验证**
  （临时回退修复 → 确认断言精确失败 → 恢复），这是 C34 的验收要求。
- **装第三方技能必须用 `npx skills add <repo> --copy`**——裸 `add` 默认建软链 + `.agents/`，违反技能目录纪律
  （实体文件、无 `.agents/`）；装完核对 `git status` 与 `.claude/skills/README.md`。**执行前先读该 README。**
- **速览只写"指向哪里"，不写"发生了什么"**：FIX-LEDGER 等主文件的速览/状态卡区块只留索引与当前状态字段，
  过程明细、门禁读数、出网账、轮次计数等一律进 `docs/history/` 归档；单段速览超 ~500 字即触发"该进 history"自查。
- **轮次计数不手写进文档**：`dev 领先 N 笔`、`本笔落地后 N` 等计数改用 `git rev-list --count origin/dev..HEAD` 现查，
  避免每次落笔重算重写、与 git 历史失同步。
- **关键读数不靠"排上去的自动化"取证**（#52 乙，主人 10-08 深夜的字）：一次性 `at` 任务跨过机器停机会
  **静默消失且零回执**——事后分不清"它跑了但失败"与"它根本没存在过"（10-08 实测：10-07 排的两枚在
  `qoder_cron list` 里连条目都没了，而那一刻机器是关着的）。⇒ 要长期盯的数必须由**产生它的那个进程写一份
  盘上覆写式落痕**，到场只读文件、不问"任务跑没跑"；本机已有两例：`web/runtime/refresh-progress.json`
  与 `data-service/runtime/hotspot-state.json`（两者都不受 ds 重启、也不受机器重启影响）。
  判据＝**排不排自动化只影响"何时读到"，不许影响"读不读得到"**。
